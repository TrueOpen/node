# TrueOpen Node RPC

This is the public RPC surface of a TrueOpen node: what it exposes, how its two
non-standard conventions work, and where the exhaustive per-method reference
lives.

Two things behave differently here than in a stock Cosmos SDK chain, and both
will break a client that assumes the default. Read [Hash encoding in
REST](#hash-encoding-in-rest) and [Pagination](#pagination) before writing an
integration.

## Transports

| Transport | Default port | Surface |
|---|---|---|
| gRPC | 9090 | `hub.v1.Query`, `hub.v1.Msg`, `task.v1.Query`, `task.v1.Msg`, and the two event streams |
| REST | 1317 | gRPC-gateway projection of the query methods that carry an HTTP binding |
| CometBFT RPC | 26657 | Consensus-level endpoints: blocks, tx broadcast, ABCI queries |

The gRPC surface is authoritative. REST is a projection of it: every REST path
is generated from a `google.api.http` binding on a gRPC method, so a field that
exists in REST exists in gRPC, and REST never carries a method gRPC does not.

## Services

| Service | Methods | Purpose |
|---|---|---|
| `hub.v1.Query` | 34 | Registry, staking, models and profiles, candidate pool, rewards, treasury, bridge, beacon |
| `hub.v1.Msg` | 20 | Registration, bonding, governance, model and profile lifecycle |
| `task.v1.Query` | 28 | Sessions, tasks, assignments, verification rounds, settlement |
| `task.v1.Msg` | 16 | Session and order submission, assignment, verification, settlement, evidence |
| `hub.v1.HubEventService` | 1 | Typed hub event stream |
| `task.v1.TaskEventService` | 2 | Typed task event stream |

REST exposes 63 paths, all under the `/TrueOpen/` prefix, for example:

```
GET /TrueOpen/hub/v1/model/{model_id}
GET /TrueOpen/hub/v1/builder_set/by_height/{height}
GET /TrueOpen/task/v1/session/{session_id}/order/{order_sequence}
```

The complete method-by-method reference, including every request and response
field, is generated from the pinned protobuf descriptor:

- `docs/static/node-api.md` — all registered Msg and Query RPCs.
- `docs/static/openapi.json` — OpenAPI 2.0 for the REST surface.

Both are regenerated by `make proto-gen`. They are the source of truth for field
numbers and method names; this document does not restate them.

## Addresses and denominations

Addresses are bech32 with the `trueopen` human-readable part:

```
account    trueopen1...
validator  trueopenvaloper1...
consensus  trueopenvalcons1...
```

Two denominations are in use and they are not interchangeable:

- `ubond` — the consensus staking denomination.
- `uusdc` — the business denomination, used for task fees, rewards and service
  bonds. It is carried in `HubParamsV2` rather than hardcoded.

## Hash encoding in REST

A 32-byte protocol hash is **lower-case hex**, not Base64.

Cosmos REST normally projects every `bytes` field as ProtoJSON Base64. That is
still true here for opaque blobs, but every field that carries a registered
32-byte protocol identifier — task IDs, session IDs, digests, fault IDs, commit
keys — is projected as a 64-character lower-case hex string instead, so the
value a REST client sees is the same string that appears in events, logs and
the protocol specifications.

In OpenAPI the two are distinguishable:

```jsonc
// registered 32-byte identifier
{ "type": "string", "format": "trueopen-hash32",
  "pattern": "^[0-9a-f]{64}$", "minLength": 64, "maxLength": 64 }

// opaque blob
{ "type": "string", "format": "byte" }
```

On input the REST layer accepts hex for a `trueopen-hash32` field and rejects
anything that is not canonical lower-case hex of exactly 32 bytes. For `byte`
fields it accepts the standard or URL-safe Base64 alphabet, padded or unpadded,
and always emits the canonical padded standard-alphabet form.

gRPC clients are unaffected: they exchange raw `bytes` and do no such
projection.

## Pagination

List queries use **keyset pagination only**. There is no `offset` and no
`count_total`, and the Cosmos `PageRequest` message is not accepted.

Request:

```protobuf
message QueryPageRequestV1 {
  bytes  page_token = 1;  // empty on the first page
  uint32 limit      = 2;  // 0 means the chain's max_query_page_limit
}
```

Response:

```protobuf
message QueryPageResponseV1 {
  bytes next_page_token = 1;  // empty when the walk is complete
}
```

Rules a client has to respect:

- `limit = 0` means "use the chain's maximum". A non-zero `limit` above that
  maximum is rejected with `InvalidArgument`; it is never silently clamped.
- `page_token` is opaque. Do not construct, parse or modify it. The server
  binds each token to the exact RPC method and the exact selector arguments it
  was issued for, and rejects a token replayed against a different method, a
  different selector, or a different chain.
- A token also pins the consensus height that the first page read, so every
  later page of a walk observes one consistent state. A walk that spans a long
  time can therefore fail once that height is pruned; restart it from an empty
  token.
- A non-empty `next_page_token` is only returned when the server has actually
  seen a further item, so an empty token is a reliable end-of-walk signal.

In REST, `page_token` and `next_page_token` are opaque blobs and therefore
Base64, not hex.

## Events

Typed events are published on `hub.v1.HubEventService` and
`task.v1.TaskEventService`. They carry the same registered 32-byte identifiers
as the queries, in raw `bytes` form.

Indexers should read `runbooks/event_indexer_contract.md`, which states the
ordering and delivery guarantees the streams provide.

## Versioning

The wire contract is published by the `TrueOpen/wire` repository and pinned by
this node in `wire/pin.json`, by release tag, commit and SHA-256. Pin an exact
wire release; do not track its main branch. Field numbers and registered method
names are frozen within a release, and a breaking change requires a new release
that declares it.
